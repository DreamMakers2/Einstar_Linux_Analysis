# Reconstruction integration audit (M1)

Status: 2026-11-11. Scope: what exists in the repository and the private evidence
directories, what is actually connected, and what is still missing.  This audit
includes the pre-existing design documents (`modern_pipeline_design.md`,
`vendor_pipeline_analysis.md`, `validation_plan.md`): the new `recon/` engine
implements their first stage, it does not replace the target architecture.  This audit
was written before the new `recon/` engine; it records the state that the engine
had to reconcile, including two wrong assumptions found in the existing tools.

## 1. Inventory

| area | what exists | evidence level |
|---|---|---|
| `driver/` | C++23 libusb transport, descriptor quirk handling, packet framing, reassembler, pipeline, C ABI (`ffi.h`), lossless raw recorder/replay, deterministic simulator, control channel | **offline-tested** (unit + integration + fuzz + stress; `ctest`), **never run against the scanner in this build** |
| `calib/` | recovered three-camera model, 8x5 plate spec (28.0 mm), robust BA, marginal/sandwich covariance, task-space guidance, adaptive session, 7 localisers, LM/SciPy solvers, verification, profiles | **offline-tested**, validated on the 75-image vendor corpus and synthetic Monte Carlo |
| `tools/calib/` | CCF/dump decoder, Bouguet rectification, triangulation, synthetic round trip, invariant checks, real-capture check | **offline-tested**; the real-capture check's pair mapping was **wrong** (see §3) |
| `tools/ccf/` | CCF container/key analysis | proved/validated |
| private `first-capture/` | 3 complete genuine three-camera triplets + one partial colour frame (`frame_%06d_cam{0,1,2}.pgm`) | the only genuine *scan* frames available |
| private `vendor-calib-rapid/` | 25 x 3 genuine images of the calibration plate | used for calibration research, not for scene reconstruction |
| private `einstar-profiles/` | exported factory calibration profile (JSON) | generated by `tools/calib/export_profile.py`; colour record marked stale |
| `libeinstar/` | an independent, hardware-validated reference implementation with IR-stereo depth (`src/depth.cpp`) | reference only; its CCF loader **rejects this unit's CCF variant** (see §3), and its depth module is not a dependency of this repository |
| `analysis/calibration/` | calibration audits, benchmarks, strategy Monte Carlo, session evidence | offline evidence |

## 2. What was missing before this milestone

1. **No shared frame/image data model.** `driver/` produces `Frame` objects with
   USB stream indices; `calib/` consumes image files and grid observations;
   `tools/calib` consumes PGM paths.  Nothing defined a synchronised three-camera
   observation with provenance, or the stream-to-calibration mapping.
2. **No C++ reconstruction path.** Rectification and triangulation existed only
   in `tools/calib/*.py`; there was no SGBM, no left-right consistency, no
   confidence, no depth/PLY export in the production language.
3. **No calibration-profile interface for reconstruction.** `calib/` writes CCF
   records and rich Python results; a compact, versioned, validated profile with
   an id/hash did not exist.
4. **No live/replay parity.** A recording could be replayed through the driver
   and counted, but there was no tool that turned the replayed USB stream into
   the same three-camera frame sets the reconstruction consumes.
5. **No RGB registration decision.** The colour record's inconsistency was
   documented but no pipeline consumed it; nothing prevented a stale colour
   profile from being silently applied.
6. **No diagnostics/visualisation.** No depth/confidence maps, no point-cloud
   preview, no machine-readable reconstruction report.

## 3. Wrong or outdated assumptions found

* **Stream order and orientation.** The existing `tools/calib/real_capture_check.py`
  assumed stream 0 = left IR and stream 1 = right IR, and did not rotate either
  image.  The hardware reference (`libeinstar`) documents the opposite:
  stream 0 = **right** IR rotated 180 deg, stream 1 = **left** IR as calibrated,
  stream 2 = colour rotated 180 deg.  With the old assumption the real pair
  produced 2/400 feature matches and ~2 % dense coverage.  With the correct
  mapping, ZNCC feature matching gives 292/300 matches, median |dy| 1 px and
  median disparity 523 px (Z ~ 350 mm), and a padded SGBM reaches ~40 % valid
  pixels with a median depth of ~350 mm.  This was the single largest blocker to
  real-data reconstruction and is now encoded in `recon/src/frame_set.cpp`.
* **OpenCV version.** The system OpenCV is 5.0 (`calib3d` split into
  `opencv_calib`, all modules exposed via `find_package(OpenCV 5)`); the old
  `find_package(OpenCV COMPONENTS calib3d)` picks nothing.
* **libeinstar CCF loader.** It rejects this unit's CCF records and the 6568-byte
  dump ("camera rotation is not orthonormal").  Our Python decoder proves the
  rotations are orthonormal after the recovered integer key, so the loader's
  offsets belong to a different CCF variant.  libeinstar is therefore used as an
  *algorithmic* reference (tuning, padding, per-camera principal points), not as
  a calibration source.
* **Colour.** The shipped Tex CCF is the known stale record (17.66 mm from the
  joint fit; `hasTexture:false`).  The reconstruction profile marks it `stale`
  and colour registration is skipped by default with an explicit status; geometry
  never depends on it.
* **`200x150`** is not a plate size and is not used by the reconstruction.

## 4. Status vocabulary used everywhere

| label | meaning |
|---|---|
| **implemented** | code exists and builds |
| **offline-tested** | deterministic tests or recorded data exercise it without hardware |
| **real-data demonstrated** | it has run on the genuine private frames (still not physical accuracy) |
| **live-hardware-tested** | it has run against the scanner; **nothing in the reconstruction path is in this class** |
| **unverified** | no evidence yet (colour registration, absolute accuracy) |

## 5. Blockers (honest)

* **No scanner attached** — live capture/replay of *new* data and the live
  acquisition tool remain untested; the simulator and recorded-stream replay are
  the only exercised paths.
* **No physical artefact** — absolute accuracy cannot be claimed.  Geometric
  consistency and predicted uncertainty are not a metrology certificate.
* **One unit, one language variant** — the factory profile is from the private
  capture; other units/variants are untested.
* **Colour record stale** — a replacement calibration with a jointly estimated
  colour camera is needed before RGB colour is trusted.

## 6. Integration decisions

1. New C++ engine under `recon/`, OpenCV 5, no Qt dependency, stable headers.
2. One `FrameSet` type with explicit stream mapping/orientation; every consumer
   works in calibration orientation.
3. Calibration enters only through a validated JSON `CalibrationProfile` with a
   SHA-256 id; factory and replacement profiles are interchangeable.
4. Rectification, matching, depth and PLY are C++; Python remains the research
   and calibration tooling (`calib/`, `tools/calib/`, analysis scripts).
5. Colour is opt-in and gated on a `color_status == "ok"` profile field.
6. Live and replay both produce the same `frame_%06d_cam%d.pgm` + manifest, so
   they feed the identical `reconstruct()` path.
